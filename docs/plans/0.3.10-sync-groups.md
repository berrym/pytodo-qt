# 0.3.10 Sync Groups Plan

## Overview

Implement sync groups for organized, multi-device synchronization with proper concurrency handling. This is a scaled-down, practical alternative to full user/access control that delivers immediate value.

## Goals

- Track known devices by fingerprint with user-friendly names
- Organize devices into sync groups (e.g., "Work", "Home", "Family")
- Assign lists to sync groups (controlling which lists sync where)
- Bulk sync operations with proper concurrency protection
- Clean GUI for managing devices, groups, and sync rules

## Non-Goals (Deferred)

- User accounts and authentication
- Permission levels (owner/editor/viewer)
- Multi-user collaboration on same device
- Server mode / always-on sync server

## Data Model

### Schema Changes (v4 → v5)

```sql
-- Known devices (peers we've synced with)
CREATE TABLE devices (
    id TEXT PRIMARY KEY,              -- UUID
    fingerprint TEXT NOT NULL UNIQUE, -- Ed25519 fingerprint
    name TEXT NOT NULL,               -- User-assigned name
    first_seen TEXT NOT NULL,         -- ISO timestamp
    last_seen TEXT NOT NULL,          -- ISO timestamp
    last_address TEXT,                -- Last known IP:port
    trust_level TEXT DEFAULT 'normal' -- 'normal', 'trusted', 'blocked'
);

-- Sync groups for organizing devices
CREATE TABLE sync_groups (
    id TEXT PRIMARY KEY,              -- UUID
    name TEXT NOT NULL UNIQUE,        -- e.g., "Work", "Home"
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

-- Device membership in groups (many-to-many)
CREATE TABLE device_groups (
    device_id TEXT NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    group_id TEXT NOT NULL REFERENCES sync_groups(id) ON DELETE CASCADE,
    PRIMARY KEY (device_id, group_id)
);

-- List sync rules (which lists sync to which groups)
CREATE TABLE list_sync_rules (
    list_id TEXT NOT NULL REFERENCES lists(id) ON DELETE CASCADE,
    group_id TEXT REFERENCES sync_groups(id) ON DELETE CASCADE,
    -- NULL group_id means "sync everywhere" (default behavior)
    PRIMARY KEY (list_id, group_id)
);

-- Pending syncs for offline devices
CREATE TABLE pending_syncs (
    id TEXT PRIMARY KEY,
    device_id TEXT NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    list_ids TEXT,  -- JSON array, empty = all applicable
    created_at TEXT NOT NULL,
    attempts INTEGER DEFAULT 0,
    last_attempt TEXT,
    expires_at TEXT NOT NULL  -- Auto-expire after 7 days
);
```

## Known Devices

### Automatic Device Tracking

When a sync connection is established (push or pull), the remote device's fingerprint is captured:

1. Check if fingerprint exists in `devices` table
2. If new: add to table with auto-generated name (hostname or "Device-XXXX"), prompt user optionally
3. If known: update `last_seen` and `last_address`
4. If blocked: reject the connection

**Naming is optional.** Devices are identified by fingerprint. The name is for user convenience only. Auto-discovered details (hostname, IP address) provide sufficient identification if user doesn't set a custom name.

### Device Trust Levels

| Level | Behavior |
|-------|----------|
| `normal` | Standard sync, user prompted for new devices |
| `trusted` | Auto-accept sync requests, auto-sync on discovery (configurable) |
| `blocked` | Reject all sync attempts |

### Fingerprint Update

**Use case:** User reinstalled app, regenerated keys, or got new machine but wants to treat as same logical device.

**Security considerations:**
- Fingerprint is the primary identity verification
- Allowing updates could enable impersonation attacks
- But rejecting updates creates usability friction for legitimate cases

**Solution:** Allow explicit fingerprint update with safeguards:

```python
def update_device_fingerprint(
    device_id: UUID,
    new_fingerprint: str,
    require_confirmation: bool = True
) -> None:
    """Update fingerprint for a known device.

    This is a security-sensitive operation. The old fingerprint
    is logged and the user must explicitly confirm.
    """
```

**GUI flow:**
1. User sees "Unknown device" prompt with new fingerprint
2. Option: "This is my device [DeviceName] with a new key"
3. Warning dialog: "Updating the fingerprint for [DeviceName]. Only do this if you know why the device's key changed (reinstall, new machine, etc.). The old fingerprint was: [old]. Continue?"
4. If confirmed: update fingerprint, log the change
5. Audit log entry: `Device 'MacBook' fingerprint updated from abc123 to def456 at 2026-02-03T10:30:00`

## List Sync Rules

### Sync Rule Logic

Each list has sync rules determining where it syncs:

| Rule State | Behavior |
|------------|----------|
| No rules (default) | Syncs to all non-blocked devices |
| Has group rules | Syncs only to devices in those groups |
| Private flag set | Never syncs (existing feature, takes precedence) |

```python
def get_sync_targets(list_id: UUID, online_devices: list[Device]) -> list[Device]:
    """Determine which devices a list should sync to."""
    lst = get_list(list_id)

    # Private lists never sync
    if lst.private:
        return []

    rules = get_list_sync_rules(list_id)

    # No rules = sync everywhere
    if not rules:
        return [d for d in online_devices if d.trust_level != "blocked"]

    # Has rules = sync to devices in specified groups
    allowed_device_ids = set()
    for rule in rules:
        group = get_sync_group(rule.group_id)
        allowed_device_ids.update(group.device_ids)

    return [d for d in online_devices
            if d.id in allowed_device_ids and d.trust_level != "blocked"]
```

### Rule Assignment UI

- List context menu → "Sync Settings..."
- Dialog shows:
  - Current sync mode (Everywhere / Selected Groups / Private)
  - Checkbox list of groups
  - Visual indicator of which devices will receive this list

## Concurrency Protection

### The Problem

Without protection, concurrent sync operations can cause:
- Race conditions in database writes
- Partial merges being overwritten
- Inconsistent state across devices

### Solution: Two-Level Protection

#### 1. Server-Side Sync Lock

The TCP server holds a lock during sync operations:

```python
class AsyncServer:
    def __init__(self):
        self._sync_lock = asyncio.Lock()
        self._sync_in_progress = False
        self._current_sync_peer: str | None = None

    async def handle_sync_request(self, reader, writer, peer_info):
        # Try to acquire lock with timeout
        try:
            async with asyncio.timeout(5.0):  # 5 second timeout
                async with self._sync_lock:
                    self._sync_in_progress = True
                    self._current_sync_peer = peer_info
                    try:
                        await self._process_sync(reader, writer)
                    finally:
                        self._sync_in_progress = False
                        self._current_sync_peer = None
        except asyncio.TimeoutError:
            # Send "busy" response, client can retry
            await self._send_busy_response(writer)
```

**Busy response:** When server is busy, client receives a structured response:
```json
{"status": "busy", "retry_after": 5, "current_peer": "MacBook"}
```

Client can:
- Show "Server busy, syncing with MacBook..." status
- Auto-retry after delay
- Queue the operation

#### 2. Client-Side Operation Queue

For bulk sync and user-initiated operations:

```python
class SyncQueue:
    """Manages outgoing sync operations sequentially."""

    def __init__(self):
        self._queue: asyncio.Queue[SyncOperation] = asyncio.Queue()
        self._current: SyncOperation | None = None
        self._results: dict[str, SyncResult] = {}

    async def enqueue(self, operation: SyncOperation) -> str:
        """Add operation to queue, return operation ID."""
        op_id = str(uuid4())
        operation.id = op_id
        await self._queue.put(operation)
        return op_id

    async def process_queue(self):
        """Process operations one at a time."""
        while True:
            operation = await self._queue.get()
            self._current = operation

            try:
                result = await self._execute_with_retry(operation)
                self._results[operation.id] = result
            except Exception as e:
                self._results[operation.id] = SyncResult(
                    success=False, error=str(e)
                )
            finally:
                self._current = None
                self._queue.task_done()

    async def _execute_with_retry(
        self, op: SyncOperation, max_retries: int = 3
    ) -> SyncResult:
        """Execute operation with retry on busy."""
        for attempt in range(max_retries):
            result = await op.execute()
            if result.status == "busy":
                await asyncio.sleep(result.retry_after)
                continue
            return result
        return SyncResult(success=False, error="Server busy after retries")
```

#### 3. Sync Transaction Model

Each sync operation has clear boundaries:

```python
@dataclass
class SyncTransaction:
```

## Bulk Sync

### "Sync Group" Operation

User selects a group and clicks "Sync Now":

1. Get all online devices in group
2. For each list with rules matching this group:
   - Determine sync direction (push, pull, or bidirectional)
   - Create SyncOperation for each device
3. Enqueue all operations
4. Process queue sequentially
5. Show progress: "Syncing list 'Work Tasks' to MacBook (1/3)..."
6. Show summary: "Synced 3 lists to 2 devices. 15 items merged."

### "Sync All" Operation

Sync all non-private lists to all applicable devices:

1. Get all online, non-blocked devices
2. For each list, determine target devices based on rules
3. Create operations, avoiding duplicates
4. Process queue
5. Show comprehensive summary

## Offline Queue

### Concept

When user initiates sync to an offline device, the operation is queued rather than failing:

1. User clicks "Sync Now" for offline device (or device goes offline mid-queue)
2. Operation added to persistent offline queue
3. When device comes online (via mDNS discovery), pending operations execute
4. User notified of queued syncs and their completion

### Implementation

```python
@dataclass
class PendingSync:
    id: UUID
    device_id: UUID
    list_ids: list[UUID]  # Empty = all applicable lists
    created_at: datetime
    attempts: int = 0
    last_attempt: datetime | None = None

class OfflineQueue:
    """Persistent queue for syncs to offline devices."""

    def __init__(self, storage: DatabaseStorage):
        self._storage = storage

    def enqueue(self, device_id: UUID, list_ids: list[UUID] = None) -> UUID:
        """Queue sync for offline device."""
        pending = PendingSync(
            id=uuid4(),
            device_id=device_id,
            list_ids=list_ids or [],
            created_at=datetime.now()
        )
        self._storage.save_pending_sync(pending)
        return pending.id

    def get_pending_for_device(self, device_id: UUID) -> list[PendingSync]:
        """Get all pending syncs for a device."""
        return self._storage.get_pending_syncs(device_id)

    def on_device_online(self, device_id: UUID) -> None:
        """Called when device discovered online. Triggers pending syncs."""
        pending = self.get_pending_for_device(device_id)
        for sync in pending:
            # Enqueue to active sync queue
            self._sync_queue.enqueue(SyncOperation(
                device_id=device_id,
                list_ids=sync.list_ids,
                pending_id=sync.id  # Track for cleanup
            ))
```

### Persistence

Pending syncs stored in SQLite:

```sql
CREATE TABLE pending_syncs (
    id TEXT PRIMARY KEY,
    device_id TEXT NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    list_ids TEXT,  -- JSON array, empty = all applicable
    created_at TEXT NOT NULL,
    attempts INTEGER DEFAULT 0,
    last_attempt TEXT

```

### Expiration

Pending syncs expire after configurable period (default: 7 days). Prevents queue from growing indefinitely for devices that never reconnect.

## Auto-Sync for Trusted Devices

### Concept

Devices marked as "trusted" automatically sync when discovered on the network:

1. Discovery service detects trusted device online
2. Auto-sync triggered (if enabled in settings)
3. Bidirectional merge same as manual sync
4. Status bar shows "Auto-synced with [Device]"

### Configuration

```python
@dataclass
class SyncSettings:
    auto_sync_enabled: bool = True
    auto_sync_interval: int = 300  # Minimum seconds between auto-syncs
    auto_sync_on_discovery: bool = True  # Sync when trusted device appears
    auto_sync_periodic: bool = False  # Future: periodic sync while online
```

### Implementation

```python
class DiscoveryService:
    def on_peer_discovered(self, peer: DiscoveredPeer) -> None:
        """Called when peer appears on network."""
        device = self._storage.get_device_by_fingerprint(peer.fingerprint)

        if device and device.trust_level == "trusted":
            if self._should_auto_sync(device):
                self._trigger_auto_sync(device, peer)

    def _should_auto_sync(self, device: Device) -> bool:
        """Check if auto-sync should trigger."""
        settings = get_sync_settings()

        if not settings.auto_sync_enabled:
            return False
        if not settings.auto_sync_on_discovery:
            return False

        # Rate limiting
        if device.last_sync:
            elapsed = (datetime.now() - device.last_sync).total_seconds()
            if elapsed < settings.auto_sync_interval:
                return False

        return True
```

### User Feedback

- Status bar: "Auto-syncing with MacBook..."
- Notification (optional): "Synced 5 items with MacBook"
- Sync status updates to "Synced just now"

## Edge Cases

| Scenario | Handling |
|----------|----------|
| All devices offline | Show "No devices online", offer to queue for later |
| Device removed mid-sync | Complete current operation, skip removed device |
| Group deleted with rules | Rules reference deleted group → treated as "no rules" |
| List deleted with rules | CASCADE delete removes rules |
| Fingerprint conflict | Two devices claim same fingerprint → reject newer, warn user |
| Server busy timeout | Client retries 3x, then shows error with manual retry option |
| Bulk sync partial failure | Complete what's possible, report failures in summary |
| Pending sync expires | Auto-cleanup after 7 days, no user action needed |
| Auto-sync while manual sync active | Queue auto-sync, process after manual completes |
| Trusted device discovered offline | No action (can't sync), update last_seen when actually connects |
| Rapid discovery events | Rate limit auto-sync (configurable interval, default 5 min) |

## Security Considerations

### Fingerprint Update Risks

**Risk:** Attacker intercepts network, presents new fingerprint claiming to be known device.

**Mitigations:**
1. User must explicitly choose to update fingerprint
2. Clear warning about security implications
3. Show old vs new fingerprint for comparison
4. Audit log of fingerprint changes
5. Optional: require physical verification (show code on both devices)

### Trust Level "Trusted"

**Risk:** Trusted devices auto-sync could sync malicious data.

**Mitigations:**
1. "Trusted" requires explicit user action to set
2. Still requires valid fingerprint match
3. Still respects list sync rules (private lists never sync)
4. Auto-sync is configurable (can be disabled globally)
5. Rate limiting prevents sync storms
6. Trust can be revoked at any time
7. All syncs logged for audit

### Blocked Devices

**Behavior:** Connection rejected at TCP level, no data exchanged.

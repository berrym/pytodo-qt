# v0.3.11 Web UI Complete Overhaul — Mobile Access Mega Release

**Status:** Planning
**Goal:** Transform the web UI from a read-mostly prototype into a fully interactive, professional-grade mobile experience that delivers near-parity with the desktop app — the kind of experience modern users expect from any real productivity app on their phone or tablet.

**Core Principle:** Privacy-first, self-hosted, LAN-first (no cloud required), but architecturally ready for the 0.4.x server mode and eventual optional cloud access for users who want it.

---

## Current State (What Exists)

The web UI today is a minimal SPA served by an embedded aiohttp server on the qasync event loop:

- **API:** 10 REST endpoints (list/item CRUD, toggle, status)
- **Frontend:** Vanilla JS (451 lines), mobile-first CSS (337 lines), PWA with service worker + offline queue
- **Can do:** View lists (dropdown selector), toggle completion, add items (plain text only), delete items, display due dates/tags/pomodoro as read-only text

## Architecture Decisions

### Keep What Works
- **aiohttp on qasync** — single-thread, no locks, proven pattern
- **Vanilla JS** — no build step, <50KB total, simple maintenance
- **Service worker + offline queue** — already implemented, extend it
- **3-second polling** — acceptable for Phase 1; WebSocket upgrade path exists for 0.4.x
- **No authentication** — LAN trust model for 0.3.x; auth comes in 0.4.x

### New Architectural Choices
- **Server-side NLP parsing** — `nlp_parser.py` is pure Python, no Qt dependency, perfect for the API
- **Single-page app with client-side routing** — hash-based routes (`#/lists`, `#/board`, `#/search`) for view switching without page reloads
- **Component-based vanilla JS** — small render functions, no framework, but organized into logical components
- **CSS custom properties** — extend the existing theme system for all new UI elements
- **Touch-first interactions** — swipe, pull-to-refresh, long-press, all via pointer events
- **Responsive breakpoints** — phone (<600px), tablet (600-1024px), desktop (>1024px)

## Phase 1: API Expansion

Extend `api.py` to expose everything the frontend needs. All new endpoints follow the existing patterns (JSON request/response, `_schedule_save_and_refresh` after writes, private list exclusion).

### New Endpoints

```
POST   /api/parse                              NLP text parsing (returns ParseResult as JSON)
GET    /api/lists/{list_id}/board               Items grouped by kanban column
PATCH  /api/items/{item_id}/move               Move item to kanban column
GET    /api/tags                                All known tags across non-private lists
GET    /api/lists/{list_id}?q=...&tags=...      Filtered item query
PATCH  /api/lists/{list_id}/columns             Add/remove/rename/reorder columns
PATCH  /api/items/{item_id}/parent              Set/clear parent_id (subtask management)
```

### Enhanced Existing Endpoints

**`POST /api/lists/{list_id}/items`** — Accept all fields:
```json
{
  "reminder": "Buy groceries tomorrow p1 @shopping",
  "parse_nlp": true,
  "priority": 1,
  "due_date": "2026-03-16",
  "due_time": "14:00:00",
  "tags": ["@shopping"],
  "parent_id": "uuid-or-null",
  "estimated_pomodoros": 2,
  "recurrence_type": "weekly",
  "recurrence_interval": 1
}
```
When `parse_nlp` is true, run `nlp_parser.parse(reminder)` server-side and apply extracted fields (client can override any).

**`PUT /api/items/{item_id}`** — Accept ALL mutable fields:
```json
{
  "reminder": "...",
  "priority": 1,
  "due_date": "2026-03-16",
  "due_time": "14:00:00",
  "tags": ["@shopping"],
  "board_column": "In Progress",
  "parent_id": "uuid-or-null",
  "estimated_pomodoros": 2,
  "recurrence_type": "weekly",
  "recurrence_interval": 1,
  "recurrence_end_date": "2026-06-01",
  "recurrence_end_count": 10
}
```

**`GET /api/lists/{list_id}`** — Add to response:
```json
{
  "id": "...",
  "name": "...",
  "board_columns": ["To Do", "In Progress", "Done"],
  "wip_limits": {"In Progress": 3},

```

**`GET /api/lists`** — Add to each list object:
```json

  "completed_count": 2,
  "overdue_count": 1,

```

**`_item_to_json()`** — Expose all fields:
```json

  "id": "...",

  "priority": 2,
  "complete": false,
  "due_date": "2026-03-16",
  "due_time": "14:00:00",
  "tags": ["@shopping"],
  "time_spent": 1500,
```

## Phase 2: Frontend — Core Navigation & Layout

Replace the current single-screen layout with a proper mobile app structure.

### Bottom Navigation Bar
Four tabs, fixed at bottom (standard mobile pattern):
- **Home** — list selector + items view (list or board mode, user's choice)
- **Add** (+) — floating action button or center tab, opens smart add sheet
- **Search** — search/filter view
- **More** — settings, about, connection status

### View Mode Toggle (List ↔ Board)
Matches the desktop app exactly: list and board are **two view modes of the same screen**, not separate navigation destinations. The user toggles between them in-place while staying on the same list.

- **Toggle control** in the header: segmented button (List | Board), mirroring the desktop's toolbar toggle buttons
- Switching view mode keeps the same list selected, same scroll context
- View mode preference persisted in `localStorage` (per-user, not per-list — matches desktop `config.database.view_mode`)
- Keyboard shortcut not applicable on mobile, but desktop web users get the same `Ctrl+Shift+B` toggle
- Both views share the same data — switching is instant, no re-fetch needed
- All item actions (toggle, delete, edit, add) work identically in both views

### View Structure (Hash Routing)
```
#/                  → Home view (list or board mode, user's choice)
#/search            → Search/filter
#/item/{id}         → Item detail sheet
#/settings          → Settings/status
```

### Header
- Dynamic title based on current view
- List selector (dropdown or dedicated list picker view)
- **View mode toggle** — segmented List|Board button (only shown on Home view)
- Connection status indicator (green dot = connected, amber = offline)

### Layout
- Phone: single column, bottom nav, full-width cards
- Tablet: sidebar list selector + main content area, optional split view for item details
- Shared: sticky header, fixed bottom nav, scrollable content area with overscroll behavior

The primary view. Must feel native-quality on mobile.

- Collapsible under parent (tap chevron to expand/collapse)
- Indented with left border accent
- Parent shows progress badge
- Can create subtasks from parent's context menu

### Sorting
- Sort button in header: priority, due date, alphabetical, created date
- Sort direction toggle (asc/desc)
- Persisted in localStorage

### Overdue Highlighting
- Calculate client-side from `due_date` + `due_time`
- Red text + red left accent for overdue

- "2 days overdue" / "Due tomorrow" relative text
- Overdue items pinned to top option

### Pull to Refresh
- Standard overscroll gesture triggers data reload
- Spinner animation during refresh

### Empty States
- "No items yet — tap + to add your first task"

## Phase 4: Frontend — Smart Add Experience

The add experience must be as good as the desktop's SmartInputWidget.

### Smart Input Sheet
- Slides up from bottom (modal sheet pattern)
- Large text input with NLP preview
- As user types, sends text to `POST /api/parse` (debounced 300ms)
- Shows extracted entities as colored chips below input:
  - 📅 Date chip (blue) — tap to edit with date picker
  - ⏰ Time chip (blue) — tap to edit with time picker
  - 🔴 Priority chip (orange) — tap to cycle
  - 🏷️ Tag chips (teal) — tap X to remove, tap + to add
  - 🔄 Recurrence chip (green) — tap to edit
  - 🍅 Pomodoro chip (purple) — tap to edit estimate
- **Quick action buttons** below chips:
  - Priority selector (!, !!, !!!)
  - Date picker (native `<input type="date">`)
  - Tag selector (shows known tags as toggleable chips)
  - Recurrence picker (preset options: daily, weekly, monthly, yearly, custom)
- Submit button: "Add" (primary color, full width on phone)
- List selector: which list to add to (defaults to current)
- Column selector: which kanban column (if in board view)

### Fallback for Offline
- When offline, items added to offline queue with all metadata
- NLP parsing happens client-side as a simple fallback (basic regex for dates, priorities, tags — doesn't need to match full parser)

## Implementation Order

The phases above are logical groupings, not necessarily sequential. Recommended implementation order for maximum impact:

1. **API expansion** (Phase 1) — foundation everything else builds on
2. **Core navigation + list view overhaul** (Phase 2 + 3) — immediately visible improvement, includes view mode toggle infrastructure
3. **Smart add** (Phase 4) — the second most-used action after viewing
4. **Item detail/edit** (Phase 5) — closes the biggest interaction gap
5. **Kanban board** (Phase 6) — implements the board side of the view mode toggle (list side done in step 2)
6. **Search & filter** (Phase 7) — high-value for real usage
7. **List management** (Phase 8) — necessary for standalone mobile use
8. **Polish & native feel** (Phase 9) — refinement pass
9. **Offline enhancement** (Phase 10) — hardens the existing offline support

## Success Criteria

When v0.3.11 ships, a user should be able to:

1. Open their phone browser, navigate to `http://<desktop-ip>:8080`
2. Install as PWA ("Add to Home Screen")
3. View all their lists and items with full metadata
4. Add items using natural language ("Buy groceries tomorrow p1 @shopping")
5. Edit any item field (text, priority, date, time, tags, recurrence, pomodoro estimate)
6. Toggle completion with swipe or tap
7. Delete items with swipe and undo
8. View and interact with kanban board (move cards between columns)
9. Search across all lists, filter by priority/date/tags/status
10. Create and manage lists
11. Create subtasks under any item
12. Work offline and have changes sync when reconnected
13. Have the experience feel like a native app, not a web page

**The bar:** A non-technical user should not feel like they're missing features compared to "real" apps like Todoist, Things, or TickTick — except for features we intentionally don't have (like cloud sync, which is a feature, not a limitation, for our users).

## Relationship to Future Versions

### 0.3.12 — PySide6 Port
- Web UI code has ZERO Qt dependency in the frontend (pure HTML/JS/CSS)
- API handlers use `QTimer.singleShot` (trivially portable to PySide6)
- No changes needed to web UI for the port

### 0.4.x — Server Mode
- All API endpoints designed here become the server mode API
- Add authentication layer (sessions, tokens) on top of existing routes
- Add TLS termination
- Headless mode: just the web server without Qt GUI
- WebSocket upgrade for real-time sync (replace polling)

### 0.5.x+ — Native Mobile / Cloud
- PWA proves out mobile patterns and UX
- Same API serves native mobile apps
- Optional cloud relay for remote access (zero-knowledge encrypted)
- Push notifications via Web Push API or native push

**This web UI is not throwaway work.** Every API endpoint, every UX pattern, every interaction design carries forward. The frontend HTML/JS is the only part that might eventually be superseded by native apps, and even then the PWA remains as a universal fallback.

## Non-Goals for v0.3.11

- **Authentication/TLS** — deferred to 0.4.x (LAN trust model is fine for now)
- **Multi-user** — deferred to 0.4.x (server mode prerequisite)
- **Push notifications** — requires HTTPS/service worker push, deferred to 0.4.x+
- **WebSocket real-time sync** — polling is acceptable; WebSocket in 0.4.x
- **Native mobile apps** — this PWA IS the mobile app for now
- **Cloud relay** — 0.5.x+
- **Pomodoro timer control from mobile** — display only (timer runs on desktop); future consideration
- **JS framework migration** — vanilla JS serves us well at this scale

Fifth prerelease of the v0.3.11 series. b5 is a discoverability and refinement release: the AddTodo dialog now exposes inline subtask creation through every reachable surface, the NLP parser silently strips connective tissue from the reminder during natural-speech entry, the calendar's hour-grid floor matches the half-hour rhythm Google and Apple Calendar enforce, and a long-standing hardcoded color reads through the theme palette. Everything in v0.3.11b1 through b4 still applies — see [v0.3.11b1](v0.3.11b1.md), [v0.3.11b2](v0.3.11b2.md), [v0.3.11b3](v0.3.11b3.md), and [v0.3.11b4](v0.3.11b4.md) for the full feature set. This page covers only what changed between b4 and b5.

## ⚠ macOS Sequoia (15.x) and later — first-launch note

Same as every prior beta in the series: the DMG is ad-hoc signed, so Sequoia and later block first launch by default.

**System Settings path:**

1. Try to open the app, get the block dialog, click **Done**.
2. Open **System Settings → Privacy & Security**.
3. Scroll to the Security section — *"pytodo-qt was blocked to protect your Mac"*.
4. Click **Open Anyway**, enter your password, click **Open** on the re-prompt.

**Command-line shortcut:**

```bash
xattr -rd com.apple.quarantine /Applications/pytodo-qt.app
```

macOS Sonoma (14.x) and earlier can still use the legacy right-click → Open path.

## Added

### Subtask creation surfaced across the AddTodo dialog (closes #9)

The parser has supported inline subtask syntax since v0.3.11b1 (`": "`, `" with tasks "`, `" with subtasks "`, `" including "`), but the capability was effectively undiscoverable from the dialog. Three legs land together so the resiliency-by-design parity is whole rather than partial:

- **Smart-input placeholder** rewritten to demonstrate the syntax: `e.g. Plan trip tomorrow at 3pm @errands p1: book flight, pack`. A user reading the placeholder discovers date, tag, priority, and the colon-syntax for subtasks in one example.
- **`SUBTASK` `EntityKind`** added to the parser. Recognized inline-subtask syntax now emits a single span covering the delimiter and items list, displayed as a `Subtasks (N)` chip in the smart input. Parse-time confirmation that the syntax was understood, alongside the existing chips for date, time, tag, priority, recurrence, etc.
- **Advanced disclosure subtasks field**: a multi-line `QPlainTextEdit` under the Tags row, one subtask per line. The field is populated from the smart-input parse result via the existing sync, so opening Advanced after typing inline syntax shows the recognized items as editable lines. The advanced-mode submit path reads the field and writes one child task per non-empty line. Users who prefer fields over syntax now have a discoverable explicit path; users who prefer syntax see their input round-trip through the field.

### NLP filler / connective phrase extraction (closes #11)

Natural-speech inputs frequently contain connective tissue between extracted entities — `"it's a"`, `"remind me to"`, `"i need to"`, `"don't forget to"`, `"let's"`, `"make sure to"`, and similar — that has no task content but had been surviving in the reminder text. The reproducible case from b4 testing (`"buy groceries tomorrow at 11am tomorrow @errands it's a high priority"`) produced a reminder of `"buy groceries it's a"` — every intended entity extracted correctly, but the connective fragment between them leaked through.

`EntityKind` gains a `FILLER` member. `core/intents/en.yaml` adds a `filler_phrases` section listing 32 conservative multi-word connective fragments. `_extract_fillers` runs after every other extraction pass so claimed entity boundaries act as natural delimiters; whole-word matching prevents intra-word matches; reservation only happens on regions free of existing entity spans. `_build_reminder` is unchanged — it already excludes every reserved span from the residual.

The dictionary is intentionally conservative — only multi-word phrases ship. Single particles like `"the"` / `"a"` / `"an"` are context-sensitive (legitimate parts of `"feed the dog"`) and stay out for now. A future evolution may add context-aware single-word handling; the current pass keeps false-positive risk near zero.

The smart input renders `FILLER` chips with a muted gray color so the parse-time recognition is visible to the user without competing visually with intent-bearing chips.

## Fixed

### Calendar minimum visible bar height (closes #10)

`_MIN_VISIBLE_MINUTES` in `core/calendar_layout.py` raised from 10 to 30. The previous value produced ~10 px of bar at the default 60 px/hour week-view zoom — above the perception threshold but too thin to hold a label or line up with the gridline. 30 minutes maps to ~30 px at the default zoom, comfortably above the perception threshold, holds a one-line label, and lines up with the half-hour gridline so floored bars feel grid-native rather than arbitrary. Matches the half-hour visual rhythm Google Calendar and Apple Calendar use as their effective floor.

### Calendar event_date color reads through the theme palette (closes #21)

`gui/widgets/calendar_view.py` was hardcoding `#9333EA` for the event_date color at two sites (bar paint and legend swatch). The theme palette already defined `EVENT_DATE` entries (`#7C3AED` light, `#A78BFA` dark) used by the smart-input chip surface, but the calendar wasn't reading them. Both sites now resolve through `get_colors()`, so the same entity reads the same color across the smart-input chip surface and the calendar bar/legend surfaces, and a theme switch updates both surfaces without further wiring.

Second prerelease of the v0.3.11 series. Ships fixes for two user-visible rendering bugs and a complete rewrite of the macOS system-notification path. Everything in v0.3.11b1's notes still applies — see [v0.3.11b1](v0.3.11b1.md) for the full feature set (installers, calendar, smart-add, kanban, NLP, settings, mobile access). This page covers only what changed between b1 and b2.

## ⚠ macOS Sequoia (15.x) and later — first-launch note

Same as b1: the DMG is ad-hoc signed, so Sequoia and later block first launch by default.

**System Settings path:**

1. Try to open the app, get the block dialog, click **Done**.
2. Open **System Settings → Privacy & Security**.
3. Scroll to the Security section — you'll see *"pytodo-qt was blocked to protect your Mac"*.
4. Click **Open Anyway**, enter your password, click **Open** on the re-prompt.

**Command-line shortcut:**

```bash
xattr -rd com.apple.quarantine /Applications/pytodo-qt.app
```

macOS Sonoma (14.x) and earlier can still use the legacy right-click → Open path.

## Fixed

### System notifications (Linux, Windows, and infrastructure)

- Migrated from Qt's `QSystemTrayIcon.showMessage` to [`desktop-notifier`](https://github.com/samschott/desktop-notifier) (MIT). One async helper (`_notify(title, body)`) replaces the five `showMessage` call sites, the permission request is wired on startup via `UNUserNotificationCenter.requestAuthorization`, and the runtime import is deferred so the app still launches on machines where the dep isn't installed yet.
- **Linux (libnotify):** unchanged in fidelity, now routed through a better-maintained library with proper app-name + icon resolution.
- **Windows (WinRT):** notifications now carry full title + body via `UNUserNotificationCenter`'s Windows equivalent, fixing the empty-body banners the Qt path had been producing.
- **macOS Sequoia 15.x with ad-hoc signing: unchanged visual outcome.** See Known limitations below — this turned out to be a bundle-identity constraint that no runtime code path can work around. The migration still lands as infrastructure for when Developer ID signing arrives in a future release.

### Calendar week view — recurring and future-dated task rendering

- Daily-recurring tasks no longer flip the rest of the week to green (completed) after you finish today's occurrence. `_ProjectedItem` proxies for future dates were inheriting the template's `complete` / `completed_at` state; they now override both so a projection is always treated as a future occurrence that hasn't happened yet.
- Non-recurring tasks dated in the future no longer render as overdue (red) when viewed from an earlier day. The `_as_of_for_viewing_day` reference moment for future viewing days was end-of-day, which asked "will it be overdue by midnight?" for any incomplete task with a due_time; it now clamps to `current_time`. Past-day historical semantics unchanged.
- Both fixes are coupled: either fix alone leaves the visual broken in a different color (green ↔ red). They shipped together in one commit (`a512084`).

### Calendar auto-advance

- Recurring-task anchor now advances correctly when the wall-clock day crosses while the app is open.

## Known limitations

### macOS Sequoia 15.x + ad-hoc signing: notifications render as a generic "PyTodo-Qt Notification" placeholder banner

On macOS Sequoia (15.x) and later, the ad-hoc-signed DMG build cannot deliver notifications with full title + body. What you see is a fallback banner with the Python rocketship icon and the text "PyTodo-Qt Notification" — no custom title, no body.

**Why:** when Python code inside a PyInstaller `.app` calls `UNUserNotificationCenter.addNotificationRequest`, macOS traces the caller up through `NSBundle.mainBundle` and finds the embedded `Python.framework` bundle rather than `pytodo-qt.app`. Because the dispatch happens under a different bundle identity than the one registered in System Settings → Notifications, and the app is only ad-hoc signed, macOS refuses to honor the registered permission and emits its generic placeholder banner. This is the same bundle-identity constraint captured in the earlier memo abandoning the notification-icon fix.

**What would actually fix this:** Developer ID signing + notarization, which requires an Apple Developer Program membership ($99/year). This is not planned for the v0.3.x series. Adding it in a future release would make macOS trust our bundle identity and resolve both this text issue and the earlier icon issue in one move.

**Workarounds today:** none via code. If you rely on system notifications on macOS, the in-app status-bar toast (bottom-right of the window) still surfaces every reminder and pomodoro transition. The web UI at `http://localhost:8080` (from another device) also shows active reminders.

### Other

- Downloading the DMG via `gh run download` or any other mechanism that strips the `com.apple.quarantine` xattr will suppress the first-launch permission prompt. Download from the browser on the release page instead, so Gatekeeper sees the quarantine flag and macOS triggers the permission flow.
- First-party release tags are still unsigned (ad-hoc only). Developer ID signing + notarization is deferred indefinitely — the cost/benefit for a zero-userbase hobby project doesn't justify the $99/year spend.
